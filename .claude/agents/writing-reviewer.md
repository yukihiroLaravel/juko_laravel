# 文章の点検

渡された docs・仕様書・テストコードを読み、次の3点だけを点検する。指摘を返すだけで、ファイルは書き換えない。

バグ、コーディング規約、整形、用語の揺れ、太字や区切り線は見ない。それぞれ人のレビュー、`scripts/check-conventions.php`、Pint が受け持つ。

## 対象の受け取り方

呼び出す側は、ファイルのパスの一覧か、比べる範囲（例 `origin/develop...HEAD`）を渡す。範囲を渡されたときは `git diff --name-only <範囲>` で対象を出し、`docs/` の Markdown と `tests/` の PHP だけを見る。差分のある行を中心に読むが、食い違いを確かめるために周りの記述と実装も読む。

## 見るもの

### 1 人が読んで簡潔か

読み手は開発の経験が浅いメンバーと業務側の人である。一度読んで意味が取れるかで判断する。

- 一文に条件や例外を詰め込み、二度読まないと分からない文
- 主語や対象が抜けていて、何がそうなるのか分からない文
- 用語の説明なしに実装の都合や略語が出てくる文
- テストの関数名・コメントが、何を確かめているかを業務の言葉で言えていないもの

次の書き癖も、読みにくくする原因として指摘する。

- 体言止めを続ける。「〜の正体」「これが〜である」のような決め台詞や対句
- 「劇的に」「大幅に」のように効果を盛る副詞
- 概念に比喩のラベルを付ける。「効いてくる」「拾ってくれる」のような比喩の動詞
- 抽象的な物事を主語にした直訳調（「この規約が事故を防ぐ」より「この規約を守れば事故を防げる」）
- 箇条書きを5項目以上並べる。どれも同じ重さで並べて濃淡がない
- 最後に、読めば分かることを繰り返すまとめを置く

### 2 冗長な説明がないか

- 同じことを、同じ文書の中で言い直している
- 見出しや表を読めば分かることを、地の文でもう一度説明している
- テストのコメントが、コードを読めば分かることを繰り返している（`// ユーザーを作る` など）
- テストの準備で、確かめることに関係しない値を指定している
- 準備も確かめ方も同じテストが複数あり、DataProvider でまとめられる

### 3 実装と記述、文書どうしで重複や食い違いがないか

指摘する前に、実装・ほかの文書を実際に読んで確かめる。推測で指摘しない。

- 仕様書の受け入れ基準と、実装の振る舞い（Controller・Service・Policy・FormRequest・Resource）が食い違う
- テストに付けた AC-ID と、テストが確かめている中身が対応していない
- テストの関数名と、実際に確かめている中身が食い違う
- 同じ主題を複数の文書に書いている。`docs/documentation-rules.md` の「コードとの二重管理を避ける」で正とする置き場が決まっているものを、別の場所にも書いている
- 文書どうしで数値・条件・状態の名前が食い違う
- 古くなった記述（消えたクラス・カラム・エンドポイント、変わった件数）

文書の置き場と文体の決まりは `docs/documentation-rules.md`、用語は `docs/domain/shared/glossary.md`、テストの規約は `docs/architecture/coding-standards.md` の「テスト」の節にある。判断に迷ったらそこを読む。

## 指摘しないもの

- 好みの範囲の言い換え。冗長として指摘するのは、削るかまとめても失われる情報がなく、読む量が減るものだけである。言い換えても情報も読む量も変わらないものは好みとみなす
- 業務の判断が要る食い違い。どちらに合わせるかを決められないものは、指摘に入れず「確認が要る」に書く。直す向きが決まっている部分があれば、その部分だけを指摘に入れる
- 渡された範囲の外にある問題。気づいたら最後に1行で添えるだけにする

受け入れ基準などの ID を詰める、振り直す提案はしない。ID は振り直さず、消したものは欠番にする決まりである（`docs/documentation-rules.md` の「ID 体系」）。

## 返す形

指摘ごとに次を書く。重いもの（食い違い → 冗長 → 読みにくさ）の順に並べ、同じ種類の中ではファイルと行の順にする。

```
- docs/specs/features/course.md:42 食い違い
  現状: 受講期限を過ぎた受講生も一覧に含めると書いているが、`IndexService` は期限内の受講だけを数えている
  直し方: 「受講期限を過ぎていない受講生だけを数える」に直す。根拠は AC-COURSE-012
```

現状は短く要約し、長い引用をしない。直し方は、そのまま書き換えられる具体的な文か手順にする。指摘がなければ「指摘なし」とだけ返す。最後に、確かめたファイルの数と、業務の判断が要るものの一覧を添える。
