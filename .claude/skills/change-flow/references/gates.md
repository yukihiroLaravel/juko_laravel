# 関門で提示する形

2つの関門はどちらも AskUserQuestion で聞く。依頼者には開発の経験が浅い者が多い前提で書く。

共通の原則は3つである。

- 業務の言葉で書く。クラス名・テーブル名・カラム名・ファイルパスを出さない
- 判断に必要なものだけを出す。全文を読ませない
- 選択肢に「承認」以外の出口を必ず用意する。承認しか押せない関門は関門ではない

## 関門1 起票の承認

起票のファイルを作る前に聞く。

### 質問文に載せる内容

```
この変更で行うことを整理しました。これで進めてよいですか。

変更する振る舞い
  ・受講の登録時に、講座が定員に達している場合は登録できないようにする
    （AC-ENROLL-003 を変更）
  ・定員に達しているかの判定は、登録の直前に行う

変更する範囲
  ・受講の登録を受け付ける入口
  ・受講を作る処理
  ・定員の判定

対象外
  ・定員そのものの設定機能
  ・すでに定員を超えている講座の是正
```

### 選択肢

| 選択肢 | 意味 | 次にすること |
|---|---|---|
| この内容で進める | 承認 | 起票を書いて段2へ |
| 変更する振る舞いが違う | 何を作るかの取り違え | 段0へ戻って聞き直す |
| 範囲が広すぎる、狭すぎる | どこまでやるかの認識差 | 範囲を詰め直す |
| 対象外に入れたいものがある | やらないことの追加 | 対象外を足して聞き直す |

## 関門2 テストの承認

失敗するテストを書いたあと、実装に入る前に聞く。

ここが仕様の確定点である。承認されたものを実装するので、ここで見落とした観点は実装にも入らない。

### 見せないもの

- テストのコード
- テストクラス名・メソッド名・ファイルのパス
- ファクトリ・シーダー・アサーションの話

コードを見せると、読めない人は判断できないまま承認する。関門を通した記録だけが残り、何も止まらなくなる。

### 質問文に載せる内容

テストの関数名は日本語で業務の視点で書く決まりになっている。ほぼそのまま箇条書きに写せる。

```
実装の前に、何を確かめるかを決めました。これで合っていますか。

確かめること（AC-ENROLL-003 に対応）

  ・定員に空きがある講座には、受講生を登録できる
  ・定員がちょうど埋まっている講座には、登録できない
  ・登録できなかったとき、受講は1件も作られない
  ・定員が設定されていない講座には、何人でも登録できる

確かめないこと

  ・同時に複数の登録要求が来たときの動き
  ・定員を後から減らしたときの既存の受講の扱い
```

境界の値を必ず1つは入れる。「ちょうど定員」「ちょうど期限日」のような、間違いが出やすい点である。

「確かめないこと」を書くのは、依頼者が「それも見てほしい」と言える余地を作るためである。書かないと、見ていないことに気づけない。

### 選択肢

| 選択肢 | 意味 | 次にすること |
|---|---|---|
| この内容で実装に進む | 承認 | 段5へ |
| 確かめる観点が足りない | 抜けの指摘 | 段3へ戻ってテストを足す |
| 確かめることが業務と違う | 仕様の取り違え | 段3へ戻って書き直す |
| 対象の前提が違う | もっと手前の誤り | 段0へ戻る |

## 迷ったとき

関門を通すかどうかで迷うくらいなら通す。実装が終わってから取り違えが分かると、捨てる量が桁違いになる。

逆に、関門を増やしすぎない。段ごとに聞くと、依頼者は読まずに承認するようになる。関門はこの2つだけにする。
