# ディレクトリ構成と各文書の役割

## 全体像

```
.
├── AGENTS.md（または CLAUDE.md）    エージェント向けの薄い入口。索引と絶対注意点のみ
└── docs/
    ├── README.md                    全体索引
    ├── documentation-rules.md       このプロジェクトでのドキュメント運用ルール
    │
    ├── domain/                      業務レイヤ（システムより長生きする）
    │   ├── README.md                コンテキスト索引
    │   ├── context-map.md           コンテキスト間の関係と用語の対訳
    │   ├── open-questions.md        未確定事項
    │   ├── shared/
    │   │   └── glossary.md          真に全社共通の語のみ
    │   └── <context>/
    │       ├── glossary.md          そのコンテキストの用語
    │       ├── business-rules.md    そのコンテキストの業務ルール
    │       └── business-flow.md     業務の流れ（システムの有無によらない作業）
    │
    ├── specs/                       システム仕様（現行仕様・上書き更新）
    │   ├── README.md                索引と運用
    │   ├── features/                画面に紐づかない機能
    │   │   └── <機能>.md            機能単位の現行仕様
    │   └── screens/                 画面の現行仕様
    │       ├── README.md            画面一覧と構成方針
    │       ├── conventions.md       全画面共通パターン
    │       └── <screen>.md          個別画面（共通からの差分のみ）
    │
    ├── architecture/                システム構成
    │   ├── overview.md              技術スタック・全体構成・ディレクトリ
    │   ├── data-model.md            テーブル定義
    │   ├── api.md                   エンドポイント
    │   └── <subsystem>.md           サブシステムの実装構成
    │
    ├── adr/                         意思決定記録（追記のみ・過去は不変）
    │   ├── README.md                一覧
    │   └── NNNN-<title>.md
    │
    └── changes/                     変更単位の作業指示（実装後に削除）
        ├── template.md
        └── <change-name>.md
```

## 何をどこに書くか

| 書きたいもの | 置き場所 | テンプレート |
| --- | --- | --- |
| 顧客業務の用語定義 | `docs/domain/<context>/glossary.md` | `templates/glossary.md` |
| 顧客業務のルール | `docs/domain/<context>/business-rules.md` | `templates/business-rules.md` |
| 業務の流れ（誰が何をするか） | `docs/domain/<context>/business-flow.md` | — |
| コンテキスト間の対応関係 | `docs/domain/context-map.md` | `templates/context-map.md` |
| 先方への確認事項 | `docs/domain/open-questions.md` | `templates/open-questions.md` |
| 画面以外のシステムの振る舞い | `docs/specs/features/<機能>.md` | — |
| 画面の現行仕様 | `docs/specs/screens/<screen>.md` | `templates/screen.md` |
| 全画面共通のパターン | `docs/specs/screens/conventions.md` | `templates/screen-conventions.md` |
| データ構造・API・実装構成 | `docs/architecture/` | — |
| 技術選定の理由 | `docs/adr/NNNN-<title>.md` | `templates/adr.md` |
| これから作る変更 | `docs/changes/<name>.md` | `docs/changes/template.md` |

## domain

システム要件より寿命が長く、AI の出力品質に直結します。受託で先方の業務設計が絡む場合、**ここが最も投資効果が高い**領域です。

### 用語集が最重要

「案件」「受注」「引当」「締め」が**顧客業務で何を指すか**。これがないとエージェントは一般的な意味で解釈します。人間の新メンバーなら周囲に聞いて修正しますが、**エージェントは疑わずに書き切る**ので被害が大きくなります。

用語集に**書かないもの**があります。テーブル名・カラム名・状態値の一覧・画面での表示制御は業務の語彙ではありません。実装との対応は specs 側が持ちます。

### コンテキスト分割

**「同じ言葉の意味が変わる境界」がコンテキストの境界です。判定基準はこれだけ。**

```markdown
# sales/glossary.md
受注 — 顧客の発注意思が確認された状態。確度と金額を持つ。
       ※出荷可能性は問わない（fulfillment の「受注」とは別概念）

# fulfillment/glossary.md
受注 — 在庫引当対象となった確定注文。sales の受注のうち、
       与信通過かつ納期確定したものだけがここに来る。
```

**最初から分けないこと。** 境界は設計で決めるものではなく、業務を理解する過程で**見つかる**ものです。着手時点で切ると必ず間違え、間違えた境界の修正は用語集の書き換えより高コストになります。

先方の部門構成をそのまま境界にしないこと。組織図は政治や人事の産物で、意味の境界とはズレます。出発点としては有用ですが、判定基準はあくまで**用語の意味が変わるか**に置きます。

`shared/` は放置すると何でも入る置き場になります（shared kernel の罠）。「全コンテキストで完全に同一の意味を持つ」ものだけに絞り、迷ったら各コンテキスト側に置いてください。

### context-map.md が分割後の最重要文書

バグと認識齟齬は**境界をまたぐ翻訳**で起きます。「片方に存在しない概念」「1 対 N に変わる」といった非対称性を明示しないと、エージェントは素朴に 1 対 1 マッピングしたコードを書きます。

この文書だけはテーブル名やキー対応を含んでよい例外です。境界をまたぐ翻訳を示すのが役割だからです。

## specs

画面以外のシステムの振る舞いを機能単位のファイルとして恒久的に置き、上書き更新します。

ワークフロー（イベントモデル）・処理の順序・判定の閾値・バリデーション範囲・状態遷移・取込のルールがここに属します。

これから作る変更は規模によらず `docs/changes/<name>.md` に起票して進めます。実装で決まった振る舞いは現行仕様のファイルへ反映し、経緯は Git 履歴と ADR が持ちます。

### 現行仕様に書くか起票だけで済ませるか

| 判断 | 条件 |
| --- | --- |
| 現行仕様へ反映する | 仕様の判断が必要 / 社内・先方の合意が要る / 実装後も参照される振る舞い |
| 起票だけで済ませる | バグ修正、文言変更、リファクタ、既存仕様の範囲内の実装 |

変更のたびに仕様ファイルを増やすと、機能単位で引ける索引が壊れます。既存のファイルへ上書きするのが原則です。

### 1 ファイルが複数の処理系統を扱うときは対象を宣言する

同じ機能ファイルに、入口の違う複数の系統（例 PDF からの取込と、画像からの取込）が同居することがあります。このとき節の冒頭に**その節がどの系統に適用されるか**を書きます。書かないと、片方の系統のしきい値を直したつもりで、もう片方まで巻き込んで壊します。

同じ値が別のファイルに独立して書かれていることもあるため、上書きの前に値で `grep -rn` を打ち、範囲を確かめてから直します。

### spec はコンテキストで分割しない

改修は複数コンテキストにまたがるため、所属させると迷子になります。代わりに冒頭で宣言します。

```markdown
## 関連コンテキスト
- 主: sales (BR-SALES-003, BR-SALES-011)
- 従: accounting (BR-ACCT-002 の締め処理と競合しうる)
```

これはエージェントへの読み込み指示としても機能します。

## specs/screens

画面は「寿命が長く、小さな変更が頻繁に起きる」性質のため、変更単位の起票とは別の恒久的な置き場を持たせます。

画面仕様を変更単位の文書だけに置くと、1 年後に「現在の仕様は 3 つの起票を合成しないと分からない」状態になります。**エージェントにとって最悪の状態です。**

### conventions.md を先に作る

一覧画面が 40 個ある場合、40 ファイルに同じことを書くのは維持不可能です。共通パターンを `docs/specs/screens/conventions.md` に括り出し、個別画面は**共通からの差分だけ**を書きます。

差分だけ、を守るために置き場は 3 段で考えます。**振る舞いの実体は `features/`、全画面に効く見せ方と操作は `screens/conventions.md`、個別画面はその 2 つからの差分だけ**です。個別画面に共通と同じ記述が現れたら、例外を書いているのか、ただ写しただけかを確かめます。写しただけなら消します。

### Figma との切り分け

| ツール | 担当範囲 |
| --- | --- |
| **Figma** | レイアウト、余白、色、コンポーネントの見た目 |
| **マークダウン** | 振る舞い、状態、バリデーション、権限、遷移 |

マークダウンで見た目を書いても劣化した Figma にしかなりません。逆に **Figma には「エラー時にどうなるか」「権限がない人に何が見えないか」が書けません。** そこがエージェントが勝手に埋める領域なので、マークダウンの価値をここに集中させます。

### 画面には所属コンテキストを書く

「注文一覧」の「注文」がどのコンテキストの注文かは画面名から判別できません。**画面は複数コンテキストが混ざる唯一の場所**でもあるため（ダッシュボード等）、どの数字がどちらの定義かを明記しないと画面内で用語が二重になります。

## architecture

技術スタック・データモデル・API・実装の構成を置きます。specs との境界は「振る舞いか、構成か」です。

- ステータスがどう遷移するか → specs
- そのステータスを持つテーブルの定義 → architecture
- 何を判定して何を保存するか → specs
- どのクラスがその責務を持つか → architecture

## changes

変更単位の作業指示を置きます。**一時的な文書であり、実装が終わったら削除します。**

残すべき内容は削除を待たず恒久文書へ反映します。ただし反映する時機は内容によって違います。業務ルール（domain）・技術選定（ADR）・未確定事項は着手の初期に反映します。テストの内容では覆らない判断だからです。システムの振る舞い（specs）とデータ構造（architecture）は実装が固まってから反映します。早く書くと、途中で振る舞いが変わったときに誤った記述が残ります。反映をすべて実装後に回すと、消すときに判断の背景ごと失われます。恒久文書の更新は任意ではなく必須の工程として扱ってください。

起票は採番せず、内容が分かるファイル名で識別します。

## adr

**時点の記録**であり、追記のみで過去は書き換えません。方針が変わったら新しい ADR を書き、古い ADR はステータスだけを更新します。

ドキュメント構成を再編したときも、判断の内容と結論は書き換えません。文書が移動した場合の参照パスだけは追随させ、リンクが切れた ADR を残しません。廃止した章立てのように移動先が 1 対 1 で決まらないものは、`docs/adr/README.md` に読み替え表を置いて対応づけます。

## AGENTS.md（CLAUDE.md）

**薄い入口**に保ちます。ここに詳細仕様を書くと `docs/` と二重管理になり、必ず片方が腐ります。

置くもの。

- このシステムが何か（1 段落）
- 実装前に必ず押さえる絶対注意点（数行。取り違えると致命的なもの）
- `docs/` の索引
- 用語の解釈ルール（コンテキストごとの用語集が唯一の正であること）
- 実装時の禁止事項
- 実装後に更新すべき文書の表
- 仕様が不足しているときの振る舞い
