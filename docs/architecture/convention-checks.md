# 規約の検査手段

`coding-standards.md` と `documentation-rules.md` に定めた規約を、どこまで機械で判定できるかを整理する。エージェントを使った開発では、規約を文章で示すだけでは守られたかどうかを確かめられない。この文書は、どの規約を機械の検査に載せ、どの規約を人間のレビューに残すかを決めるための対応表である。

既存コードには規約策定前の書き方が残っており、一括での作り替えは行わない。そのため「既存の違反を許したまま、新しく増える違反だけを落とす」という扱いが要る。区分 B がそれにあたる。

## 判定の区分

| 区分 | 意味 | 扱い |
|---|---|---|
| A | 機械で判定でき、既存の違反が 0 件 | 直ちに検査に載せ、違反があれば落とす |
| B | 機械で判定できるが、既存に違反がある | 基準線を記録し、そこから増えた分だけを落とす |
| C | 機械で検出できるが誤検知が混ざる | 警告として出し、落とさない |
| D | 機械で判定できない | レビューの観点として残す |

区分 A と B が検査の対象になる。C は出すだけで判断は人に委ねる。D は検査に載せず、レビュー時の指摘項目として `coding-standards.md` の重大度と対応させる。

## 検査手段の割り当て

| 手段 | 受け持つ範囲 | 実行する場所 |
|---|---|---|
| Laravel Pint | 整形と PSR-12 | 編集直後・継続的インテグレーション |
| PHPStan レベル6 と基準線 | 型の誤りと型宣言の欠落 | 継続的インテグレーション |
| Rector | 旧い記法 | 継続的インテグレーション |
| `scripts/check-conventions.php` | 本文と構造の走査で判定できる規約 | 編集直後・継続的インテグレーション |
| `php artisan route:list --json` | ルートの名前と形 | 検査には載せておらず、レビューで出力を確かめる |
| 人間 | 設計・命名・責務の妥当性 | レビュー |

検査スクリプトは 1 本にまとめ、編集直後のフックと継続的インテグレーションの両方から同じものを呼ぶ。判定を 2 か所に書くと、いずれ食い違う。

## 検査の実行

`scripts/check-conventions.php` が 26 項目を判定する。既定では 24 項目を見て、`--merge` を付けたときに残りの 2 項目（CHK-TEST-06・CHK-DOC-06）を加える。違反があれば終了コード 1 を返し、違反の場所と直し方を出す。

```bash
scripts/dc composer check-conventions
```

呼び出す場所は 3 つある。

| 場所 | 呼び方 | 効き方 |
|---|---|---|
| 編集直後（`.claude/settings.json` のフック） | `scripts/dc php scripts/check-conventions.php --quiet` | `.php` と `.md` を書いた直後に Pint で整形してから検査し、違反があればその場で書き手に返す |
| 実装中の評価 | `scripts/dc composer check-conventions` | 既定の 24 項目を見る |
| 継続的インテグレーション | `composer check-conventions-merge`（PHP が入った環境のため直接呼ぶ） | 26 項目すべてを見て、取り込む前に落とす |

いずれも同じスクリプトを呼ぶ。フックは手元で気づくため、継続的インテグレーションは取りこぼしを止めるためにある。

検査には見る時機が 2 つある。作業中に見てよいものと、取り込む前にだけ見るものである。起票の残骸（CHK-DOC-06）とテストが参照する受け入れ基準の実在（CHK-TEST-06）は後者にあたる。起票は着手から実装完了まで存在しているのが正しい状態であり、受け入れ基準は実装が固まってから仕様へ反映するため、作業中はテストの AC-ID が先行する。編集のたびに咎めると手順そのものが進まない。

既定は作業中に見るものだけとし、`--merge` を付けたときに全部を見る。呼ぶ回数が多いほうを既定にしている。作業中は編集のたびに走るが、取り込む前の検査は継続的インテグレーションで1回走るだけである。

判定は PHP で書いている。シェルで書くと macOS と継続的インテグレーションで `grep` の方言差に当たること、公開メソッドのような構造の判定は字句解析でないと文字列やコメントの中を誤検出することが理由である。

検査を足したときは、違反を仕込んで実際に落ちることを確かめる。鳴らない検査は、無いより悪い。

区分 C の検査は `scripts/check-conventions.php` にまだ実装しておらず、現状はレビューで見る。

## 区分 B の扱い

区分 B の扱いは 2 通りに分けた。仕組みを増やさないことを優先している。

| 対象 | 扱い |
|---|---|
| 型宣言（CHK-TYPE-01） | PHPStan の基準線に記録し、そこから増えた分だけを落とす |
| それ以外 | 違反を修正して 0 件にし、区分 A に移す |

型宣言の未宣言は数が多く、修正しきるのは現実的でない。PHPStan の基準線は既存の機能であり、これを使うぶんには独自の仕組みが増えない。

それ以外を区分 A に寄せることで、検査スクリプトは「違反が 0 件であること」だけを見ればよく、規約ごとの記録を持たずに済む。記録を持つ仕組みは、それ自体が更新の手間と食い違いの原因になるため作らない。
