# コーディング規約

このプロジェクト固有の実装ルールを定める。Laravel の汎用的なベストプラクティスは `laravel-best-practices` スキルを参照し、汎用ルールと衝突する場合はこちらを優先する。

既存コードには本規約が策定される前の書き方が残っている。新規実装と修正のときに本規約を適用し、既存コードの一括での作り替えは行わない。

## 配置と命名

すべてのレイヤー（Controller・FormRequest・Service・Resource・Enum・Test）は、コンテキストごとのサブディレクトリに配置し、`{行う処理}{接尾辞}.php` で命名する。

## コントローラー

- サービスクラスはメソッドインジェクションで受け取る。コンストラクタインジェクションにしない
- データベーストランザクションはコントローラーで管理する。`DB::transaction()` でサービス呼び出しを囲み、サービス内では張らない

## バリデーション

- FormRequest で実装し、1エンドポイント1ファイルとする。複数エンドポイントでの共有を禁止する
- Enum を定義している値の制御は `Rule::enum(GenderEnum::class)` を使い、`in:1,2,9` のようなリテラルの列挙をしない。Enum を持たない単純な選択肢（並び順など）は `in:` で書いてよい

## サービス

- 複数のモデルが関与するビジネスロジックを置く。単一モデルで完結するならモデルに置く
- 公開メソッドは `__invoke` 1つのみとする。フローの可視化を優先し、必要なら private 関数で責務を分離する
- 入力値は `FormRequest::validated()` の配列で受け、認証ユーザーなど validated 以外のコンテキストは引数で明示的に受け取る
- 別のサービスを使うときは、コンストラクタで `private readonly` のプロパティとして受け取る。`new` で生成しない
- Resource が参照するリレーションは、サービスかコントローラーで `with()` して読み込んでおく。開発環境とテストでは遅延ロードを例外にしている（`Model::shouldBeStrict()`）ため、読み込み忘れは 500 になる。読み込むリレーションの名前を変えたら、参照している箇所を `grep -rn` で洗う

## モデル

- キャストを必ず定義し、明示的な phpdoc を記述する
- セキュリティ性が高いカラム（password・token など）は `$hidden` に設定する

## マイグレーションとテーブル設計

- 外部キーは `foreignIdFor` と `constrained` を使い、参照先への制約を必ず張る

```php
$table->foreignIdFor(Instructor::class, 'manager_id')->nullable()->constrained()->comment('講師ID');
```

- テーブルとカラムには必ず `->comment()` をつける
- `timestamp` 型は 2038 年問題のため避けて `datetime` を使う。`timestamps()` ヘルパも同様に使わない

## Enum

- テーブルの識別子カラムには Enum を活用し、`app/Enums/{コンテキスト}/~Enum.php` で定義する
- バッキング型は格納値の性質で選ぶ。状態や種別を表すカラム（`status`・`type` など）は string backed を既定とする
- 定義した Enum はモデルの `casts()` でキャストし、返り値の phpdoc に配列シェイプで書く。書かないと静的解析がキャストを認識せず、比較が常に偽と判定される
- 取得したモデルの値は Enum どうしで比べる（`$course->status === StatusEnum::PUBLIC`）。`->value` や `'public'` のような文字列と比べない。キャスト後の値は Enum なので、文字列との比較は常に偽になる。クエリの `where` に渡す値は `->value` でよい
- 既存にクラス定数がある場合は、Enum の導入と合わせて削除し、参照箇所も Enum 参照に書き換える

対象はテーブルのカラムに格納する状態と種別に限る。次のものは Enum にしない。

| 対象 | 例 | 扱い |
|---|---|---|
| 並び順の指定 | `nick_name`・`created_at` | リクエストの検証で値を絞る |
| 集計期間の指定 | `today`・`week`・`month` | 同上 |
| 単なる既定値 | 進捗の初期値 | 定数のままでよい |

これらはテーブルに保存されず、列挙の集合が業務の意味を持たない。Enum にするとクラスだけが増える。

## 公開状態での絞り込み

受講生に見せるもの、受講生の進捗や修了の集計に使うものは、公開されている講座・チャプター・レッスンに限る（BR-SHARED-009）。絞り込みを漏らすと、受講生に非公開のものが見えたり、集計が受講生の画面と合わなくなったりする。

- 公開されているものは、既存のリレーションとスコープで取る。講座のチャプターは `Course::publicChapters()`、チャプターのレッスンは `Chapter::publicLessons()`、チャプターとレッスンのクエリでは `->public()` を使う。講座にはスコープがないので、`status` を Enum の値で絞る。取得したあとに配列で絞り直さない
- 総数と完了数のように比で表す値は、分母と分子を同じ条件で絞る。片方だけ公開に絞ると、率が 100% を超えたり下がったりする
- 空のコレクションに `every()` を使うと真になる。「すべて完了している」を判定するときは `isNotEmpty()` と併せて使う
- スコープを `#[Scope]` 属性で定義するときは、メソッド名に `scope` の接頭辞を付けない。付けると同じスコープが2つの名前で定義される

## 認可

判定の基準は `docs/specs/features/authorization.md` に集約している。コード上の置き場は次のとおりである。

- コントローラーは `$this->authorize('動詞', $モデル)` を呼ぶだけにする。判定の条件は Policy に書く
- 持ち主・配下の講師・公開状態・受講期限による判定を、サービスとコントローラーに書かない。`$user->id` と比べて拒否するような書き方がこれに当たる。受講生がいる講座は削除できない、のような業務上の拒否は、サービスから例外を送出してよい
- 持ち主・配下の講師・公開状態・受講期限のように、同じ対象に複数の条件があるときも、Policy の1つのメソッドにまとめる。別の操作と同じ判定なら、Policy の中で既存のメソッドに委ねる

## ルーティング

- 複数形を利用する（ユーザー登録なら `POST users`）
- コンテキストに合わせて `prefix` と `name` を活用し、エンドポイントには必ず `name()` を定義する
- ルート定義はロール別のファイルに置く（ADR-0001）

## Resource

- API レスポンスのスキーマに利用し、ビジネスロジックの実装を禁止する。整形と表示のみを行う

## 型と PHP 全般

- 関数の返り値の型と引数のタイプヒントを必ず定義する。規約の策定前からある未宣言は `phpstan-baseline.neon` に記録している
- 日付ライブラリは特に理由がない限り `CarbonImmutable` を利用する
- `config` 以外での `env()` 関数を禁止する
- 配列操作よりコレクションメソッドを優先し、宣言的に記述する
- `empty()` の利用を避け、`=== null`・`=== ''`・`->isEmpty()` などで明示的に判定する
- PHP と Laravel ともに最新のメソッドや機能を積極的に利用する
- 型や前提条件で起こりえない分岐を書かない。認証済みのルートでの `$user?->`、検証済みの値への `isset()`、到達しない `default` などである
- コメントには、名前と型から読めないことだけを書く。たとえば、なぜその書き方にしたかや、null と空配列のように返り値の意味が分かれるときの区別である
- 型と同じ内容の `@var` や、処理を言い直すだけのコメントは書かない。使わなくなったコードはコメントにして残さず消す

## コード品質

- 行の長さは 120 文字を上限とする PSR-12 に従う。Pint は整形を判定するが、行の長さは判定しない
- PHPStan（larastan）のレベル6を通す
- 整形は Laravel Pint、自動リファクタリングは Rector で行う

実行するコマンドは `AGENTS.md` にある。

## テスト

- 対象の Controller や Service の配置に対応したサブディレクトリに `{行う処理}Test.php` で作成する
- AAA パターンを利用し、必ずコメントで `Arrange`・`Act`・`Assert` を記述する
- 対応する受け入れ基準があるときは、テスト関数の直前に AC-ID をコメントで書く。関数名は日本語のまま保つ

```php
/** AC-ENROLL-002 */
public function test_同じ受講生を同じ講座に二重登録できない(): void
```

仕様は `docs/specs/` とテストの2か所に分かれる（作業中は起票にも書く）。ID を書いておくと `grep -rn 'AC-ENROLL-002'` で両方を同時に引ける。書かないと、仕様を変えたときにどのテストを直すべきかを検索で辿れない。

- テスト関数名は日本語で書き、システム用語を避けて業務と利用者の視点の言葉を使う。レスポンスのキーや変数名をそのまま使わず、対応する日本語の名称にする（`average_progress_rate` ではなく平均進捗率）
- 参照データ（マスタなど）はシーダー、それ以外（ユーザーなど）はファクトリで用意する
- 講師のファクトリは、既定で区分がマネージャーの講師を作る。講師としての権限を確かめるテストでは、区分に講師を指定する。指定しないとマネージャーの分岐しか通らず、講師の分岐の誤りを検出できない
- 具体例に加えて、どんな入力でも成り立つ性質に着目したテストを検討する。例えば、同じ操作を2回行っても結果が変わらないこと（冪等性）である

実行環境とスイートの構成は `docs/architecture/overview.md` にある。

## レビュー時の重大度

コード差分や PR をレビューするときは、指摘ごとに重大度を付ける。

| 重大度 | 対象 |
|---|---|
| `must` | セキュリティ・データ整合性・規約の必須違反（`env()` の直接利用、認可漏れ、外部キー未設定、トランザクション欠如） |
| `should` | 設計規約からの逸脱、テスト不足（配置と命名の違反、型注釈漏れ、振る舞いの変更にテストがない） |
| `nits` | 軽微な指摘や好みの範囲 |
