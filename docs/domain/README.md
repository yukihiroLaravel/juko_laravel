# 業務知識

受講管理の業務そのものを記述する。システムが存在しなくても成り立つ事実だけを置き、システムの振る舞いは `docs/specs/` に置く。

## 文書一覧

| 文書 | 内容 |
|---|---|
| [shared/glossary.md](shared/glossary.md) | 用語集。このプロジェクトでその言葉が何を指すか |
| [shared/business-rules.md](shared/business-rules.md) | 業務ルール。`BR-SHARED-<連番>` で参照する |
| [open-questions.md](open-questions.md) | 未確定事項。`Q-<連番>` で参照する |

## コンテキストを分割していない

業務領域はまだ分割していないため、用語集と業務ルールは `shared/` に1つずつ置いている。受講管理という単一の業務のなかで、同じ言葉が立場によって別の意味を持つ場面が今のところ見つかっていないためである。

分割は設計で決めるものではなく、業務を理解する過程で見つかるものである。次のいずれかが起きたときに分割を検討する。

- 同じ用語に「講師から見ると、受講生から見ると」と注記を書き始めた
- 担当者が自分に関係あるルールを探せなくなった
- ルールの変更頻度が明確に違うまとまりが現れた

分割するときは、業務ルールの ID は振り直さずに文書だけを移す。ID は主題に紐づくものであり、置き場所に紐づくものではない。コンテキストが2つ以上になった時点で `docs/domain/context-map.md` を作り、境界をまたぐ用語の対応を記述する。

## 書くときの注意

- 主語を業務・人・書類にする。システムを主語にした文が書けてしまったら、それは `docs/specs/` に属する
- 講座の内部構造・状態値の一覧・集計の計算式といったシステムの都合は書かない
- `docs/specs/` を参照しない。参照は specs から domain への一方向に保つ（`open-questions.md` の影響範囲欄だけが例外）
- どのルールがどこで実装されているかを知りたいときは `grep -rn 'BR-SHARED-006' docs/` で追う
