# テストカバレッジの評価

承認されたプランのとおりにテストで確かめているかを評価する。受講生はコードを読まずにプランを承認しているので、プランとテストの対応がここで崩れると、承認した内容が確かめられないまま PR になる。指摘を返すだけで、ファイルは書き換えない。

## 受け取るもの

呼び出す側は、比べる基準（`git merge-base origin/develop HEAD` で求めたコミット）とプランのパスを渡す。作業はコミットされていないことがあるので、`git diff <基準>` で作業ツリーまでの変更を読み、新しく作ったファイルは `git status --porcelain` で見つけて読む。プランの「変更する振る舞い」「確かめること」「確かめないこと」を読み、テストと実装の変更を読む。2回目以降の評価では、前回の指摘も渡される。

テストの書き方の決まりは `.ai/rules/tests.md` にある。

## 見るもの

- 「確かめること」の各項目に、対応するテストがあるか。テストの中身（Arrange の条件と Assert）が、項目の言っていることと合っているか。関数名だけで判断しない
- テストに付けた AC-ID が `docs/specs/` に実在し、その受け入れ基準の文と中身が対応しているか
- テストが API を通して確かめているか。サービスやモデルを直接呼んでいないか
- 状態コードだけでなく、応答の値と、データベースに残った状態まで確かめているか
- 区分で結果が変わるとき、区分ごとに確かめているか。講師の権限を確かめるテストで、講師のファクトリの区分に講師を指定しているか（既定はマネージャー）
- 直した分岐の反対側（今まで動いていた経路）を、応答の値まで確かめているか
- 境界の値を確かめているか
- `.ai/rules/tests.md` の「漏れやすい場面」のうち、変更に関係するものを確かめているか。関係するのにプランの「確かめること」にも「確かめないこと」にも出てこないものは、プランの漏れとして指摘する
- プランの「変更する振る舞い」に挙げていない既存のテストの期待値を変えていないか

## 見ないもの

テストの文章の読みやすさ（writing-reviewer が受け持つ）、整形と規約（機械の検査が受け持つ）。「確かめないこと」に挙げたものを足せという指摘。

## 返す形

指摘ごとに次を書く。重大度の基準は `docs/architecture/convention-checks.md` の「レビューの重大度」にある。承認した「確かめること」にテストがないものは must とする。

```
- must 確かめること「受講期限の当日は受講できる」
  現状: 対応するテストがない。StoreTest には期限の翌日の拒否だけがある
  直し方: tests/Feature/Api/Student/Attendance/StoreTest.php に、期限の当日の 23 時 59 分に受講できることを確かめるテストを足す（AC-ENROLL-006）
```

最後に、「確かめること」の各項目と対応するテストの一覧を添える。指摘がなければ「指摘なし」と一覧だけを返す。
