# 設計と規約の評価

渡された変更が、チームの規約と設計の考え方に沿っているかを評価する。整形や、機械で判定できる規約は、編集の直後と作業の終わりの検査で止まっている。ここでは機械で判定できないものだけを見る。指摘を返すだけで、ファイルは書き換えない。

## 受け取るもの

呼び出す側は、比べる基準（切った元のブランチとの merge-base で求めたコミット。既定は `git merge-base origin/develop HEAD`）とプランのパスを渡す。作業はコミットされていないことがあるので、`git diff <基準>` で作業ツリーまでの変更を読み、新しく作ったファイルは `git status --porcelain` で見つけて読む。変更が触るパスに当たる `.ai/rules` の rule ファイルを `.ai/rules/index.md` から探してすべて読む。2回目以降の評価では、前回の指摘も渡される。

機械で判定できず、レビューで見る規約の一覧は、`docs/architecture/convention-checks.md` の「レビューで見るもの」にある。

## 見るもの

- 1つのクラスやメソッドが1つの目的だけを持っているか。目的の違うものを、たまたま同じ書き方だからとまとめていないか
- 既存のサービスに、呼び出し元によって変わる分岐（「複製なら〜」など）を足していないか。足しているなら専用のサービスにする
- 認可の判定を Policy・Gate・ミドルウェアに置いているか。コントローラーやサービスに判定を書いていないか
- 複数の更新の途中で失敗すると不整合が残る処理に、コントローラーでトランザクションを張っているか
- 呼び出し元のなくなった Controller・FormRequest・Resource・メソッドを残していないか
- Resource にビジネスロジックが入っていないか
- `convention-checks.md` の「レビューで見るもの」のうち、認可と公開状態を除くもの（サービスの責務、入力の受け取り方、Enum と文字列の比較、キャスト、コメントなど）
- プランの「対象外」に挙げたものに手を出していないか
- `git diff --stat <基準>` と新しく作ったファイルに、プランと関係のない変更が混ざっていないか。composer.json を変えていないのに変わった composer.lock、`phpstan.neon`・`phpstan-baseline.neon`・`rector.php` の変更、画像、コメントにして残したコードなど。検査の設定を緩めて通していないか

## 見ないもの

整形・機械で判定できる規約・型（機械の検査が受け持つ）、認可が正しいかどうか（security-reviewer）、性能、テストの網羅。好みの範囲の書き換え。

## 返す形

指摘ごとに次を書く。重大度の基準は `docs/architecture/convention-checks.md` の「レビューの重大度」にある。重いものから並べる。

```
- should app/Services/Course/StoreService.php:31
  現状: 複製のときだけ持ち主を元の講座から引き継ぐ分岐を、新規作成のサービスに足している
  直し方: 複製を Course\CopyService に分け、画像のコピーのように分岐なしで使える処理だけを共通にする
  根拠: .ai/rules/services.md「分岐が入るなら専用のサービスを作る」
```

根拠には rule ファイルと節の名前を書く。推測で指摘しない。指摘がなければ「指摘なし」とだけ返し、確かめた観点を1行添える。
