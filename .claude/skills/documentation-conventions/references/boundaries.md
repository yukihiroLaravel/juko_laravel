# domain と specs の境界

`docs/domain/` と `docs/specs/` は目的が違います。混ざると、業務ルールが機能単位に散って再利用できなくなり、実装が終わった時点で業務知識も一緒に捨てられます。

## 1. 一行での定義

| | 書いてあること |
| --- | --- |
| **`docs/domain/`** | **顧客の業務がどうなっているか。** システムが存在しなくても成立する事実 |
| **`docs/specs/`** | **そのシステムでどう実現するか。** 作ると決めたから生まれる判断 |

## 2. 「非開発者も読める」は結果であって定義ではない

domain は非開発者も読めます。これは正しい。ただし**判定基準としては使えません。**

- `docs/specs/` の受け入れ基準も先方レビューに出すので非開発者が読む
- ADR も「なぜこの方式にしたか」を説明するため先方に見せることがある
- 逆に `context-map.md` のキー対応表は、非開発者には読めないが domain に属する

読者層は境界の**副作用**として現れるもので、境界そのものではありません。判定には以下の 2 つのテストを使います。

### テスト A: リプレーステスト

> **このシステムを別の言語・フレームワークで全面的に作り直したとき、その文書は残るか?**

- **残る → domain。** 顧客の締め日や承認権限は、システムを作り直しても変わらない
- **捨てる → specs。** 「この API をこう設計する」は作り直せば消える

### テスト B: 反実仮想テスト

> **このシステムを作らなかったとしても、その記述は成り立つか?**

- **成り立つ → domain。** 「月末締め」は、システムがなくても顧客の業務として存在する
- **成り立たない → specs。** 「一覧画面は 20 件ずつ表示する」はシステムがあって初めて生じる

この 2 つを通せば、読者層を考えずに判定できます。そして結果として、domain 側には「業務を知っていれば読める文書」が集まります。順序が逆にならないよう注意してください。

## 3. 最も実用的な見分け方: 文章の主語

書こうとしている文の主語を見ます。

```
domain: 締め日を過ぎた受注は、翌月計上とする。
        └─ 主語は「受注」= 業務の事実

specs:  受注日が締め日を過ぎたとき、システムは翌月計上として登録しなければならない。
        └─ 主語は「システム」= システムの振る舞い
```

**SHALL 形式（「システムは〜しなければならない」）で書けてしまったら、それは spec です。** domain に SHALL 形式の文が現れたら、境界を越えている合図。

## 4. 対比表

| 軸 | `docs/domain/` | `docs/specs/` |
| --- | --- | --- |
| 文の主語 | 業務・人・書類 | システム |
| 寿命 | システムより長い | 作るものを変えると終わる |
| 変わる理由 | 顧客の業務が変わった | 作るものを変えると決めた |
| 更新方法 | 上書き（恒久文書） | 上書き（恒久文書） |
| 正しさを保証する人 | 先方の業務担当者 | 開発チーム |
| 粒度 | 業務領域（コンテキスト） | 機能 |
| ID | `BR-SALES-003` | `AC-ORDLIST-005` |

## 5. 同じ話題の両側 — 具体例

同じテーマが両方に現れることは普通にあります。**書き分けの粒度がこれです。**

| テーマ | `docs/domain/` に書くこと | `docs/specs/` に書くこと |
| --- | --- | --- |
| 締め | BR-SALES-003: 月末締め。締め日を過ぎた受注は翌月計上。締め後の受注は編集不可 | AC-ORD-012: 締め済み受注が開かれたとき、システムは全項目を読み取り専用にしなければならない (BR-SALES-003) |
| 権限 | BR-SALES-011: 営業担当は自部門の受注のみ閲覧できる。管理者は全部門 | AC-ORDLIST-006: 一般権限の場合、システムは自部門の注文のみ表示しなければならない (BR-SALES-011) |
| 承認 | BR-SALES-020: 500 万円超の受注は部長承認を要する | AC-APPR-003: 金額が 500 万円を超えるとき、システムは承認待ちステータスで登録しなければならない (BR-SALES-020) |
| 用語 | 「受注」= 顧客の発注意思が確認された状態（出荷可能性は問わない） | 表示項目の出典に `sales.order` を明記し、`## 関連コンテキスト` で sales を宣言 |

パターンは一貫しています。**domain は業務のルールを述べ、specs はそれをシステムでどう表現するかを述べて、末尾に `(BR-XXX)` で紐づける。**

### 内容は片方にだけ書く

```markdown
✕ specs/<機能>.md
  ## 受け入れ基準
  1. AC-ORD-012: 月末締めのため（締め日を過ぎた受注は翌月計上となり、
     締め処理後は編集不可）、締め済み受注は読み取り専用にしなければならない。
     ↑ 業務ルールの説明が spec に混入している。ルールが変わると両方直すことになる

◯ specs/<機能>.md
  ## 受け入れ基準
  1. AC-ORD-012: 締め済みの受注が開かれたとき、システムは全項目を
     読み取り専用にしなければならない (BR-SALES-003)。
     ↑ ルール本体は domain。spec は ID 参照のみ
```

## 6. 参照は一方向にする

これが混同の直接の原因になります。

```
   specs/  ──参照──▶  domain/       ◯ 正しい
   specs/  ◀──参照──  domain/       ✕ 混ざる
```

**`specs` から `domain` は参照する。`domain` から `specs` は参照しない。**

domain の業務ルールに「参照している仕様: `docs/specs/screens/<screen>.md`」のような逆参照欄を設けてはいけません。これを書くと、spec を追加・変更・削除するたびに domain 側を更新する必要が生じます。つまり **domain が spec のライフサイクルに引きずられる**、これは実質的な統合です。

「どのルールがどこで実装されているか」を知りたい場合は、逆参照を持たせるのではなく `grep -r "BR-SALES-003" docs/` で足ります。参照の一方向性を保ったまま追跡できます。

## 7. 判断に迷う典型例

| 記述 | 置き場所 | 理由 |
| --- | --- | --- |
| 「月末締め」 | domain | 顧客の業務。システムがなくても成立（テスト B） |
| 「500 万円超は部長承認」 | domain | 同上。承認は業務のプロセス |
| 「取引先コードは 8 桁の数字」 | domain | 先方のコード体系。システム都合ではない |
| 「一覧は 20 件ページング」 | `docs/specs/screens/conventions.md` | システムがあって初めて生じる。業務ルールではない |
| 「顧客名は最大 255 文字」 | スキーマ定義 | 機械的制約。ドキュメントに書くと二重管理になる |
| 「締め済み受注は読み取り専用にする」 | specs | 主語がシステム。BR-SALES-003 の実装表現 |
| 「承認画面に承認ボタンを出す」 | `docs/specs/screens/` | 画面の振る舞い |
| 「承認は取り消せない」 | domain | 業務上の性質。画面の都合ではない |
| 業務フローのイベントモデル図 | specs | 「アップロードされたら OCR にかける」はシステムがないと成立しない |
| 業務のステップ一覧（誰が何をするか） | domain | システムの有無によらず必要な作業 |
| 計算式そのもの（制度や規格が定めるもの） | domain | リプレースしても残る |
| 丸めの実装・使用ライブラリ | specs | 作り直せば変わる |
| 状態値の一覧（`pending` / `merged` 等） | specs | システムが持つ状態であり業務の語彙ではない |

判断に迷ったら **domain 側に寄せる** のが安全です。domain に書いた spec 的記述は後から移せますが、spec に埋めた業務知識は仕様を畳み込むときに失われます。

## 8. Notion との関係（非開発者の位置づけ）

「domain は非開発者も読める」という点から、Notion に置くべきか迷いやすいので整理します。

| | `docs/domain/`（リポジトリ） | Notion |
| --- | --- | --- |
| 内容 | **確定した**業務知識 | ヒアリング記録、議論、業務フロー図、合意の過程 |
| 状態 | 構造化・ID 付き | 未整理・時系列 |
| 非開発者の関与 | **読む**（更新は PR 経由） | **書く** |
| エージェント | 読む | 通常は読ませない |

流れはこうなります。

```
Notion でヒアリング・議論
        │
        │ 確定したものを構造化して転記（ID を付与）
        ▼
docs/domain/<context>/business-rules.md   ← 唯一の正
        │
        │ (BR-XXX) で参照
        ▼
docs/specs/ , docs/specs/screens/
```

Notion 側には確定内容を再掲せず、リポジトリへのリンクを置いてください。両方に業務ルールの本文があると、必ず片方が腐ります。

## 9. 迷ったときの判定フロー

```
1. その記述の主語は「システム」か?
     ├─ はい → specs
     └─ いいえ ↓
2. システムを全面リプレースしても残るか?
     ├─ はい → domain
     └─ いいえ ↓
3. 業務ルール（BR）に紐づかない機械的な制約（型・桁数・最大文字数）か?
     ├─ はい → スキーマ定義（ドキュメントに書かない）
     └─ いいえ → specs/screens/conventions.md
```

「必須」は出所で分かれます。業務ルールから導かれる必須は specs に SHALL で書いて `BR-ID` を参照し、業務ルールに紐づかない機械的な必須だけをスキーマに任せます。
