# 調査とプランの作成

依頼された変更について、関係するものを調べ、プランを返す。プランを読んで承認するのは受講生である。受講生は開発の経験が浅く、コードを読まずに判断する前提で書く。ファイルは書き換えない。Bash は読むためだけに使う。

承認はこのプランの1回だけである。承認のあとは、実装・検査・評価・/goal の判定まで止まらずに進む。プランで見落とした観点は、そのまま実装にも入らない。

## 調査

分からないことが残ったままプランを返さない。分からないまま承認を求めると、受講生は判断材料を持たないまま承認することになる。

1. `.ai/rules/index.md` を読み、変更が触るパスに当たる rule ファイルをすべて読む
2. `docs/domain/open-questions.md` を見る。依頼の主題が未確定として記録済みかもしれない
   - 依頼が暫定方針と同じ方向 → そのまま進める
   - 依頼が暫定方針を覆す方向 → その矛盾と Q-ID をプランの背景に書く。承認されても `open-questions.md` は書き換えない。変更の可否と業務ルールの確定は、答えられる人が違うためである
   - 記録がなく判断できない → 決めずに、確認が要ることとしてプランの最初に書く
3. 触る機能の `docs/specs/features/` を読み、変える受け入れ基準の ID を控える。該当するものがなければ新設になることを控える
4. `docs/domain/shared/business-rules.md` と `glossary.md` で、関係する業務ルールと用語を確かめる
5. 実装の該当箇所を読む。同じ書き方をしている箇所を `grep -rn` で探し、利用者がその経路に届くかどうかで対象と対象外に分ける。対象外にしたものは理由を控える
6. 関係する API のテストを読み、今どこまで確かめているかを控える。直す分岐の反対側（今まで動いていた経路）を応答の値まで確かめているかも見る
7. 依頼のチケットに依存先が挙がっていれば読み、応答の形などの前提を控える

## プランの形

次の見出しで書く。ここでいう業務の言葉とは、講座・受講生・受講期限のような言葉である。クラス名・テーブル名・カラム名・ファイルパスは「反映する docs」と「タスク」の節にだけ出す。

```
# <変更の要約>

## 目的
何のための変更かを1〜2文で。

## 背景
なぜ今必要か。関係する Q-ID や業務ルールの ID。暫定方針と食い違うならその旨。

## 変更する振る舞い
業務の言葉で、何がどう変わるか。既存の受け入れ基準を変えるなら AC-ID を、新しく足すなら「新設」と書く。

## 変更する範囲
責務の単位で書く（受講の登録を受け付ける入口、定員の判定、など）。ファイル名を並べない。

## 対象外
この変更でやらないこと。調査で対象外にした経路と、その理由。

## 確かめること
テストで確かめることを業務の言葉で並べる。対応する AC-ID を添える。

## 確かめないこと
今回は確かめないこと。受講生が「それも見てほしい」と言える余地を作るために書く。

## 反映する docs
更新するファイルと、何を書くか。`.ai/rules/docs.md` の「実装が終わったとき」の表に従う。

## タスク
依存の順に並べ、何に依存するかを書く。
```

## 確かめることの書き方

- 境界の値を必ず1つは入れる。「ちょうど定員」「受講期限の当日と翌日」のように、間違いが出やすい点である
- はっきりした境界がない変更（値がないときの扱いを直すなど）では、今まで動いていた側を「今までどおり」として入れる
- 区分（受講生・講師・マネージャー）で結果が変わるなら、区分ごとに書く
- `.ai/rules/tests.md` の「漏れやすい場面」のうち、変更に関係するものは、入れるかを検討する

## タスクの組み方

- 最初のタスクは、確かめることを API のテストとして書き、落ちることを確かめるもの
- 次に、テストを通す実装。テストを通すのに必要な範囲を超えない
- 新しい受け入れ基準があれば、実装と同じタスクで `docs/specs/` に ID と一文を足す
- そのあと docs の反映、最後に観点別の評価と /goal の判定
- 受け入れ基準の ID はテストを書くタスクで決める。番号は追加先ファイルの末尾に続ける

## やってはいけないこと

- 調べずに推測でプランを書く
- 対象外に挙げたものをタスクに入れる
- 既存の未確定事項を確定させる
