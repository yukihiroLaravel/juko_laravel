# ADR-0007 承認をプランの1回にし、機械の検査と観点別の評価と /goal で進める

## ステータス

承認済み (2026-11-14)

## 背景

このリポジトリは、2か月ごとに入れ替わる受講生が AI を使った開発を体験する場である。受講生に身につけてほしいのは、仕様を言葉にして AI に渡し、出てきたプランと結果を判断する力である。受講生が自分でコードを書く部分は残さない。

これまでは `change-flow` スキルで手順を定め、起票を書く前と、失敗するテストを書いたあとの2か所で承認を取っていた。起票は `docs/changes/` に置き、実装後に消していた。規約は `docs/architecture/coding-standards.md`・`docs/documentation-rules.md`・`AGENTS.md`・`documentation-conventions` スキルに分かれていた。

候補は次の3つである。(a) 今の手順を保つ。(b) cc-sdd（仕様駆動開発のツール）のように、機能ごとに要件と設計とタスクの文書を残す。(c) Claude Code のプランモードと /goal に乗せ、承認をプランの1回にする。

## 決定

(c) を採る。プランモードで依頼し、`planner` エージェントがプランを作り、受講生がプランを1回だけ承認する。プランには「確かめること・確かめないこと」を含める。承認のあとは、AI がテストから実装し、作業の終わりの機械の検査、4つの観点（セキュリティ・パフォーマンス・テストカバレッジ・設計と規約）と文章の点検の評価、/goal の判定まで進める。PR は受講生が出す。

あわせて次を決めた。

- プランは `.claude/plans/` に置き、git の管理に入れない。経緯は PR に残す
- 機械の検査は、編集の直後に整形と規約の検査、作業の終わりと継続的インテグレーションで `composer check-all` を流す。pre-commit は入れない
- 規約は `.ai/rules/` にパスごとに分けて置き、`docs/architecture/coding-standards.md`・`docs/documentation-rules.md`・`AGENTS.md`・`change-flow`・`documentation-conventions` をなくす
- 評価は2回目以降は must が出た観点だけを評価し直し、3回で残れば止めて受講生に報告する
- テストは API のテストを基本にし、テストの DB は SQLite のインメモリのままにする

## 理由

- 受講生は開発の経験が浅く、テストを書いた段階で止めて承認を求めても、判断できないまま承認する形になりやすい。確かめることをプランに業務の言葉で書けば、1回の承認で何を作り何を確かめるかを判断できる
- 承認を1回にしたので、テストを書いてから実装するまでが一続きになる。作業の終わりにテストの通過を強制しても、テストが落ちたまま止まるべき段がなく、手順と衝突しない
- 検査は全部で約30秒で終わる。作業の終わりに CI と同じものを流しても待ち時間は小さく、手元で通れば CI でも通る
- 観点を分けたエージェントで評価すると、受講生がコードを読まなくても、セキュリティや性能の問題を PR の前に直せる
- (a) は関門が2つあり、手順をスキルの文章で縛るため、規約と手順の置き場が増え続けた
- (b) は文書が機能ごとに残り続ける。受講生が入れ替わると手入れをする人がいなくなり、古い要件が今の仕様と食い違ったまま残る

## 影響

- 起動時はプランモードになり、モデルは `opusplan` を使う。サブエージェントで Opus を使うのはプランを作る `planner` だけで、effort も high にする。評価のエージェントは Sonnet にし、受講生の利用量を抑える
- `docs/changes/` と起票の残骸を見る検査（CHK-DOC-06）を廃止した
- 規約を足すときは `.ai/rules/` の該当ファイルに書き、検査に載せるかを `docs/architecture/convention-checks.md` で決める
- 評価はトークンを使うので、受講生の利用量の上限に当たらないかを運用しながら見る
- テストは SQLite で流すため、MySQL でしか起きない不具合はテストで拾えない。データベース固有の SQL を書かない規約で補う
