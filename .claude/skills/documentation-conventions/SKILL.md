# ドキュメント構成の規約

AI エージェントと人間が同じドキュメントを読む前提の運用規約です。**業務知識とシステム仕様を混ぜないこと**が全体の土台になります。

混ざると次の 2 つが起きます。業務ルールが機能単位に散って再利用できなくなり、実装が終わった時点で業務知識も一緒に捨てられます。

## まず判定する

書こうとしている記述の置き場は、次の順で決まります。**大半はこのフローだけで決着します。**

```
0. その主題は既にどこかに書かれているか? （grep -rn で確かめる）
     ├─ はい → その記述を上書きし、ID は維持する。ここで終了
     └─ いいえ ↓
1. その記述の主語は「システム」か?
     ├─ はい → specs
     └─ いいえ ↓
2. このシステムを別の言語で全面リプレースしても、その記述は残るか?
     ├─ はい → domain
     └─ いいえ ↓
3. 業務ルール（BR）に紐づかない機械的な制約（型・桁数・最大文字数）か?
     ├─ はい → スキーマ定義に任せる（ドキュメントに書かない）
     └─ いいえ → specs/screens/conventions.md
```

**3 の「必須」に注意します。** 必須には出所が 2 つあります。業務ルールから導かれる必須（「3 項目がそろわない機器は判定にかけないので入力を必須にする」）は業務判断であり、**specs に SHALL で書いて `BR-ID` を参照します。** スキーマに任せるのは、業務ルールに紐づかない機械的な必須だけです。**分岐は制約の形ではなく出所で決めます。**

判定に迷ったら **domain 側に寄せます**。domain に書いた spec 的記述は後から移せますが、spec に埋めた業務知識は仕様を上書き更新するときに一緒に失われます。

詳しい判定基準（3 つのテスト・対比表・具体例）は [references/boundaries.md](references/boundaries.md) にあります。

### 主語テストが最も実用的

```
domain  締め日を過ぎた受注は、翌月計上とする。
        主語は「受注」= 業務の事実

specs   受注日が締め日を過ぎたとき、システムは翌月計上として登録しなければならない。
        主語は「システム」= システムの振る舞い
```

**SHALL 形式（システムは〜しなければならない）で書けてしまったら、それは specs です。** domain に SHALL 形式の文が現れたら境界を越えている合図とみなします。

## ディレクトリの索引

| 置き場 | 内容 | 文の主語 | 改修時 |
| --- | --- | --- | --- |
| `docs/domain/` | 顧客の業務がどうなっているか。用語集・業務ルール・コンテキストマップ・未確定事項 | 業務・人・書類 | 上書き |
| `docs/specs/` | 画面以外のシステム仕様。ワークフロー・処理ルール・判定基準 | システム | 上書き |
| `docs/specs/screens/` | 画面の振る舞い・状態・遷移 | システム | 上書き |
| `docs/architecture/` | 技術スタック・データモデル・API・実装構成 | システム | 上書き |
| `docs/adr/` | 意思決定の記録 | — | 追記のみ・過去は不変 |
| `docs/changes/` | 変更単位の作業指示。着手時に起票し、実装後に削除する | — | 一時 |

各ディレクトリの詳しい役割とファイル構成は [references/structure.md](references/structure.md) を参照してください。

## 参照は一方向にする

```
   specs  ──参照──▶  domain       ◯ 正しい
   specs  ◀──参照──  domain       ✕ 混ざる
```

**domain から specs を参照しません。** 逆参照を持たせると spec を追加・変更・削除するたびに domain 側の更新が要り、domain が spec のライフサイクルに引きずられます。

どの業務ルールがどこで実装されているかを知りたいときは、逆参照を持たせるのではなく `grep -r "BR-SALES-003" docs/` で追います。

例外は `docs/domain/open-questions.md` の影響範囲欄だけです。未確定事項は業務の未確定とシステム仕様の未確定を 1 箇所に集めるための文書で、「どこに跳ねるか」を書けないと役に立ちません。ここに限り specs の文書名と `AC-ID` を書いてよいものとし、下の点検 grep からも除外します。**それ以外の domain 文書（glossary・business-rules・business-flow・context-map）は例外になりません。**

### specs の内部にも向きがあります

```
   screens  ──参照──▶  features       ◯ 正しい
   screens  ◀──参照──  features       ✕ 実体が 2 つになる
```

**振る舞いの実体は `features/` に置き、`screens/` は画面固有のこと（表示・操作・遷移・その画面だけの例外）を書いて、実体を `AC-ID` で参照します。** 同じ振る舞いを両方に書くと、変更のたびに両方を直すことになり、片方が必ず取り残されます。

`screens/conventions.md` に書いた共通の振る舞いを個別画面へ再掲してよいのは、**その画面に例外があるときと、その画面の従来仕様と矛盾していて打ち消しが要るときだけ**です。それ以外は共通に任せて書きません。

## A. 新しくドキュメントを書くとき

1. **同じ主題が既に書かれていないか探す** — 書こうとしている主題で `grep -rn` を打ちます。**同義の記述があれば、新しい ID を振らずにその記述を上書きします。** これを飛ばすと同じ事実が 2 つの ID で並び、参照側がどちらを見ればよいか決められなくなります。判断基準は [references/conventions.md](references/conventions.md) の「ID は主題に紐づく」にあります。
2. **判定フローで置き場を決める** — 上の 3 ステップ。迷ったら domain。
3. **テンプレートから起こす** — [templates/](templates/) に各文書の雛形があります。コメントに配置先と書き方の注意が入っています。
4. **ID を振る** — 業務ルールは `BR-<コンテキスト>-<連番>`、受け入れ基準は `AC-<機能>-<連番>`。**番号は振り直さず、削除時は欠番のまま空け、新しい主題の追加だけを末尾に足します。**
5. **同じ話題の両側を書き分ける** — domain は業務のルールを述べ、specs はそれをシステムでどう表現するかを述べて末尾に `(BR-XXX-NNN)` で紐づけます。**業務ルールの説明を specs 側へ書き写しません。** ルールが変わったときに両方を直すことになります。
6. **「対象外」を必ず書く** — 書かないとエージェントが気を利かせて過剰実装します。
7. **未確定は「未確定」と明示する** — `docs/domain/open-questions.md` に集約し、担当者・期限・暫定方針まで書きます。書かないとエージェントが空白を勝手に埋めます。

ID 規約・SHALL 形式の書き方・文体のルールは [references/conventions.md](references/conventions.md) にあります。

## B. 実装が終わってドキュメントを更新するとき

**まず、その主題が既にどこに書かれているかを `grep -rn` で確かめます。** 既存の記述があれば ID を維持して上書きし、新しい主題のときだけ末尾に足します（A の手順 1 と同じ関門です）。実装後の更新は「足す」から入りがちで、ここを飛ばすと同じ振る舞いが 2 つの ID で並びます。

そのうえで、同一 PR で次を更新します。

| 変更内容 | 更新するファイル |
| --- | --- |
| 画面の振る舞いを変えた | `docs/specs/screens/<screen>.md`（上書き） |
| 画面以外の振る舞いを変えた | `docs/specs/features/<機能>.md`（上書き） |
| データ構造や API を変えた | `docs/architecture/`（上書き） |
| 業務ルールが判明・変更された | `docs/domain/<context>/business-rules.md`（上書き） |
| 技術選定の判断をした | `docs/adr/` に**新規** ADR を追加（既存は上書きしない） |
| 方針を覆した | 旧 ADR のステータスのみ更新し、新 ADR を追加 |

**業務ルールを変えたつもりが実はシステムの振る舞いだった、という取り違えが最も起きます。** 主語がシステムなら `docs/specs/` です。

本文を直したら、**同じファイルの図（ワイヤーフレーム・mermaid）が古い振る舞いのまま残っていないかを見ます。** 受け入れ基準だけ直して図を放置すると、次に読むエージェントは図のほうを信じます。

起票（`docs/changes/`）は上表に含めません。**恒久的に残す内容は着手の初期に上表の文書へ反映し、実装が終わったら起票ファイルごと削除します。** 起票に書いた検討中の事項が確定したときも、追従させるのは恒久文書のほうで、起票は消える前提の作業メモとして扱います。起票を最新に保とうとすると、同じ内容を 2 箇所で維持することになります。

バージョン付きファイル（`*_v2.md`・`*_old.md`・`*_20260715.md`）を作らないこと。状態を表す文書は上書きし、履歴は Git に任せます。不要になった文書は残さず削除します。

## C. 既存ドキュメントを整理・レビューするとき

次の観点で点検します。機械的に検出できるものから当てると速いです。

```bash
# domain に SHALL 形式が混ざっていないか（0 件であるべき）
grep -rn 'システムは.*しなければ\|してはならない' docs/domain/

# domain から specs への参照がないか（0 件であるべき。open-questions は例外）
grep -rn '\.\./specs/\|\.\./architecture/' docs/domain/ | grep -v open-questions

# domain にテーブル名・カラム名・状態値が露出していないか
grep -rn '`[a-z][a-z_]*_[a-z_]*`' docs/domain/ | grep -v context-map

# 画面仕様が features を飛ばして業務ルールを直接参照していないか
grep -rn 'BR-' docs/specs/screens/

# 欠番になった ID への参照が残っていないか
grep -rn 'BR-XXX-0NN' docs/
```

3 番目は 0 件を目指すものではありません。ヒットしたら、**その振る舞いの実体が `features/` にあるかを確かめます。** 実体が features にあるなら画面側は `AC-ID` 参照に直し、画面固有の振る舞いなら `BR-ID` 参照のままで構いません。

ファイル単位で性質が spec 側に寄っているものは、記述単位で削るのではなく**ファイルごと移します**。ワークフロー図・処理フロー・信頼度の閾値・バリデーション範囲は、まとまって specs 側に属することが多いです。

`docs/domain/context-map.md` のキー対応表だけは例外で、テーブル名を含んでいても domain に属します。境界をまたぐ翻訳を示すのが役割だからです。

## D. まだ導入していないプロジェクトで立ち上げるとき

一度に全部作らないこと。次の順で価値が出ます。

1. **`docs/domain/shared/glossary.md`** — 用語集。コンテキストを分けずフラット 1 ファイルで開始する
2. **`docs/adr/`** — 意思決定記録。今日の判断から書き始める
3. **`docs/specs/screens/conventions.md`** — 画面共通仕様。個別画面より先に共通を固める
4. **`docs/specs/`** — 次の大きめの機能から適用する
5. **`docs/domain/` のコンテキスト分割** — 用語の衝突が実際に起きてから

コンテキストは**着手時点で切らないこと**。境界は設計で決めるものではなく業務を理解する過程で見つかるもので、先に切ると必ず間違えます。間違えた境界の修正は用語集の書き換えより高コストです。

分割の合図は次の 3 つです。

- 同じ用語に「営業では〜、経理では〜」と注記を書き始めた
- 担当者が自分に関係あるルールを探せなくなった
- ルールの変更頻度が明確に違う（受注ルールは毎月、会計ルールは年 1 回）
