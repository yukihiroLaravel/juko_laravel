# 書き方の規約

## 原則 0: 変更が起きる場所のそばに置く

| 種別 | 置き場所 | 理由 |
| --- | --- | --- |
| コードと密結合する仕様（要件・設計・画面・ADR・用語集・業務ルール） | **リポジトリ内マークダウン** | エージェントが自動で文脈に読み込む |
| 組織・プロダクト知識（オンボーディング、ロードマップ、議事録、業務フロー図） | **Notion 等** | 非エンジニアとの共有・データベース機能 |

**同じ情報を両方に書かないこと。** トピック単位で「住所」を 1 つ決め、もう片方はリンク参照に留めます。

## 原則 1: 「状態を表す文書」と「時点の記録」を分ける

改修時の扱いがここで決まります。

| 種類 | 性質 | 改修時 | 対象 |
| --- | --- | --- | --- |
| **状態を表す文書** | 常に「今こうなっている」 | **上書き更新** | glossary / business-rules / context-map / specs / architecture |
| **時点の記録** | その時の判断・出来事 | **追記のみ、過去は不変** | ADR / 議事録 / リリースノート |

**なぜ上書きしてよいのか** — 「なぜ変わったか」は ADR と Git 履歴が持つからです。ADR を書かずに恒久文書を上書きすると経緯が消えるので、**この 2 つは必ずセットで運用します。** 片方だけではどちらも機能しません。

### バージョン付きファイルを残さない

```
business-rules.md
business-rules_v2.md        ← 禁止
business-rules_old.md       ← 禁止
business-rules_20260715.md  ← 禁止
```

人間は「old は無視」と判断できますが、**エージェントは全部読んで矛盾した仕様を混ぜて実装します。** 古い仕様書がリポジトリに存在するだけで実装品質が落ちます。

不要になった文書は残さず削除します。内容が要るときは Git 履歴から取り出せます。

### 合意の証跡の残し方

受託で「この時点の要件で合意した」記録が必要な場合、ファイルを複製せず次で固定します。

- Git のタグ（例: `agreed-2026-07-15`）
- 合意時点で PDF に書き出し、Notion に添付

## 原則 2: ID による相互参照

**業務ルール → システム要件 → 設計 → タスク → テスト** を ID で一本につなぎます。「先方の業務ルールが変わった」ときに影響範囲を追えるようにするためです。

### ID 規約

| 対象 | 形式 | 例 |
| --- | --- | --- |
| 業務ルール | `BR-<コンテキスト>-<連番>` | `BR-SALES-003` |
| 受け入れ基準 | `AC-<機能または画面>-<連番>` | `AC-ORDLIST-005` |
| ADR | `ADR-<連番>` | `ADR-0007` |
| 未確定事項 | `Q-<連番>` | `Q-005` |

### 番号は振り直さない

`docs/specs/screens/` の画面仕様や `docs/changes/` の起票が `AC-XXX-003` を参照している状態で番号を振り直すと、**参照が全部壊れます。**

- 削除しても番号は**欠番のまま空ける**
- 追加は**末尾に足す**
- 連番（要件 3）ではなく最初から安定 ID（`AC-ORDLIST-003`）を使う

欠番にしたときは、なぜ欠番になったかをコメントで残します。

```markdown
<!-- BR-SALES-007 は欠番。並び順の既定値はシステムの振る舞いのため specs/ へ移した -->
```

ID を欠番にしたら、**その ID を参照している箇所を必ず洗い出して張り替えます。**

```bash
grep -rn 'BR-SALES-007' docs/
```

### ID は主題に紐づく — 改訂と追加の分岐

**ID が指すのは主題であって、そのときの記述ではありません。** 同じ主題を書き直すたびに新しい ID を振ると、同じ事実が 2 つの ID で並び、参照側はどちらを見ればよいか決められなくなります。

| 起きたこと | 記述の扱い | ID の扱い |
| --- | --- | --- |
| 同じ主題の内容が変わった（値の変更・条件の追加・出典の確定・表現の精緻化） | **上書き** | 既存 ID を**維持** |
| 主題そのものが無くなった | 削除 | **欠番**にしてコメントを残す |
| 主題の範囲が変わり、旧記述が別物になった | 旧を削除し新しく書く | 旧は**欠番**、新は**末尾に追加** |
| これまでに無い事実・振る舞いが増えた | 新しく書く | **末尾に追加** |

「追加は末尾に足す」が効くのは下 2 行だけです。**既存の主題を改訂するときに末尾へ足すと、同じ内容が 2 つの ID で重複します。** 上書きは版を消す行為ではありません。過去の版は Git 履歴が持ちます。

## 原則 3: 受け入れ基準は SHALL 形式で書く

> 「〜のとき (WHEN) / 〜の場合 (IF)、システムは〜しなければならない (SHALL)」

この定型（EARS 記法）で書くと曖昧さが消え、そのままテストケースになります。

```markdown
◯ AC-PWR-003: 未登録のメールが送信されたとき、システムは登録済みの場合と
   同一の成功メッセージを表示しなければならない。
✕ メールアドレスの存在は漏らさないよう配慮する。
```

一見自明な項目（「検索と並び替えはサーバー側で処理する」など）も明示します。書かないとフロントで配列を sort する実装が出て、ページネーションと組み合わせたときに壊れます。

## 原則 4: 「対象外」を必ず書く

書かないと **エージェントが気を利かせて過剰実装します**（パスワードリセットを頼んだら SMS 認証まで作る）。「やらないこと」の明示は AI 前提の仕様の必須項目です。

```markdown
## 対象外 (Non-Goals)
- SMS / 電話番号によるリセット
- 秘密の質問
```

## 原則 5: 未確定は「未確定」と明示する

要件は必ず一部が未確定のまま進みます。それを書かずにおくと **エージェントが空白を勝手に埋めます。** `docs/domain/open-questions.md` に集約し、担当者・期限・暫定方針まで書きます。

```markdown
## Q-005 為替レートの適用タイミング
未確定。受注時レートか請求時レートか先方確認中（担当: 田中 / 期限: 8/5）
→ 確定するまで実装は保留。仮実装する場合は受注時レートで、TODO コメント必須。
```

暫定方針で実装する場合は、コードに `TODO(Q-NNN)` コメントを必須とします。

確定したら、その内容を business-rules / glossary / 該当 spec に反映し、その項目は「確定済み」セクションへ**移動**します（削除しない）。

## コードとの二重管理を避ける

バリデーションルールをマークダウン・フロント・バックエンドの 3 箇所に書くと必ず食い違います。**更新されない画面仕様は、エージェントに嘘を教える害になります。**

| 書く場所 | 対象 |
| --- | --- |
| **マークダウンを正とする** | 業務判断が入るもの（権限による表示制御、範囲検索の仕様、ステータス遷移、絞り込みの既定値、**業務ルールから導かれる必須**） |
| **コード / スキーマを正とする** | 業務ルールに紐づかない機械的な制約（型、最大文字数、単なる入力必須）。仕様側はスキーマ定義へのリンクで済ませる |

例: 「一覧は 20 件ページング」はマークダウン、「顧客名は最大 255 文字」はスキーマ。「3 項目がそろわない機器は判定にかけないので入力を必須にする」は `BR-ID` を参照するマークダウンです。**同じ「必須」でも出所で行き先が変わります。**

「スキーマ定義」が何を指すかはプロジェクトごとに 1 つ名指しで決めます（マイグレーションか、`docs/architecture/data-model.md` か）。決めずにおくと、型と桁数が両方に書かれて食い違います。

## 文体

プロジェクトで統一します。既存ドキュメントがあれば**そのスタイルに合わせること**。新規に決めるなら次を既定とします。

- マークダウンで一系統に管理する（HTML を別に作らない）
- 文章はである調で書く
- 図解は mermaid で描く（シーケンス図・フローチャート・ER 図・状態遷移図）
- 太字記法を使わない（見出しと表で構造化する）
- 区切り線（`---`）を使わない（見出し階層で区切る）
- 説明の地の文でコロンを使わない（コード・表のセル・mermaid 構文内は許容）

図は ASCII アートより mermaid を優先します。ただし画面のワイヤーフレームは ASCII のほうが伝わることがあります。

## 明示しないとエージェントが誤る項目チェックリスト

経験的に、書かないと必ず勝手に埋められる箇所です。

- [ ] **対象外（Non-Goals）** — 書かないと過剰実装
- [ ] **未確定事項** — 書かないと空白を埋める
- [ ] **サーバー側処理かクライアント側処理か** — 書かないとフロントで配列を sort し、ページネーションで壊れる
- [ ] **検索条件は AND か OR か**
- [ ] **部分一致か完全一致か**
- [ ] **日付は範囲指定か単日か**
- [ ] **0 件時 / 読み込み中 / エラー時の挙動**
- [ ] **権限による表示差**（誰に何が見えないか）
- [ ] **所属コンテキスト**（どの用語集を参照すべきか）
- [ ] **1 対 1 か 1 対 N か**（コンテキスト境界をまたぐ場合）
- [ ] **既定値**（フィルタ・並び順・初期表示件数）
- [ ] **丸めと単位**（どの桁で、どの向きに丸めるか）
