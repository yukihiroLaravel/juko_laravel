# PHP 全般

このプロジェクト固有の書き方を定める。Laravel の汎用的なベストプラクティスは `laravel-best-practices` スキルにあり、衝突する場合は `.ai/rules` を優先する。

既存コードには規約を決める前の書き方が残っている。新しく書くときと直すときに適用し、既存コードを一括で作り替えない。

## 配置と命名

Controller・FormRequest・Service・Resource・Enum・Test は、コンテキストごとのサブディレクトリに置き、`{行う処理}{接尾辞}.php` で命名する。

## 型

- 関数の返り値の型と引数の型を必ず宣言する。規約を決める前からある未宣言は `phpstan-baseline.neon` に記録している（CHK-TYPE-01）
- 日付は特に理由がない限り `CarbonImmutable` を使う（CHK-TYPE-02）
- `empty()` を使わず、`=== null`・`=== ''`・`->isEmpty()` などで明示的に判定する（CHK-TYPE-04）
- 型や前提条件で起こりえない分岐を書かない。認証済みのルートでの `$user?->`、検証済みの値への `isset()`、到達しない `default` などである

## 書き方

- `config` 以外で `env()` を呼ばない（CHK-TYPE-03）
- 配列操作よりコレクションのメソッドを優先し、宣言的に書く
- PHP と Laravel の新しいメソッドや機能を使う
- 行の長さは 120 文字までとする PSR-12 に従う。Pint は行の長さを判定しない

## 単一責務を優先する

1つのクラスやメソッドには1つの目的だけを持たせる。同じ記述が複数の箇所にあっても、目的が違うならまとめない。たまたま同じ書き方になっているだけなら重複とはみなさない。Policy の各メソッドに並ぶ持ち主の判定がその例である。

まとめてよいのは、同じ目的で、同じ理由で変わるものだけである。目的の違うものをまとめると、片方の都合で直したときにもう片方が壊れる。「同じ処理が何度も書かれている」と判断する前に、それぞれの目的が同じかを確かめる。

## デッドコードは消す

呼び出し元のない Controller・FormRequest・Resource・メソッドは削除する。使わなくなったコードをコメントにして残さない。

## データベース固有の SQL を避ける

テストは SQLite のインメモリで、開発環境と本番は MySQL で動く。どちらでも同じように動くよう、クエリは Eloquent とクエリビルダーで書く。`DB::raw()`・`selectRaw()`・`whereRaw()` などで、片方のデータベースにしかない関数（日付の関数、`GROUP_CONCAT`、`FIELD()` など）を使わない。どうしても生の SQL が要るときは、両方で動くことを確かめ、理由をコメントに書く。

## コメント

- コメントには、名前と型から読めないことだけを書く。なぜその書き方にしたかや、null と空配列のように返り値の意味が分かれるときの区別である
- 型と同じ内容の `@var` や、処理を言い直すだけのコメントを書かない
