# テスト

テスト戦略の原則は `CLAUDE.md` の「テストの方針」にある。ここでは書き方を定める。

## 層と配置

- テストは API のテストを基本にし、`tests/Feature/Api/` の下に、対象のコントローラーの配置に対応したサブディレクトリを切って `{行う処理}Test.php` で置く
- サービスやモデルを直接呼ぶテストは新しく書かない。API から同じ条件を作るとテストが重くなる計算だけを例外とし、そのときは理由をテストクラスの phpdoc に書く
- テストの DB は SQLite のインメモリである。SQLite と MySQL で動きの違う SQL を避ける決まりは `php.md` にある

## 形

- AAA パターンで書き、コメントで `Arrange`・`Act`・`Assert` を必ず書く（CHK-TEST-02）
- 対応する受け入れ基準があるときは、テスト関数の直前に AC-ID をコメントで書く。仕様を変えたときに `grep -rn 'AC-ENROLL-002'` で仕様とテストを同時に引けるようにするためである。書いた AC-ID が `docs/specs/` に実在するかは CHK-TEST-06 で検査する

```php
/** AC-ENROLL-002 */
public function test_同じ受講生を同じ講座に二重登録できない(): void
```

- テスト関数名は日本語で書き、システム用語を避けて業務と利用者の視点の言葉を使う。レスポンスのキーや変数名をそのまま使わず、対応する日本語の名称にする（`average_progress_rate` ではなく平均進捗率）（CHK-TEST-03）

## 確かめる中身

- 状態コードだけでなく、応答の値と、データベースに残った状態まで確かめる
- 認可は区分（受講生・講師・マネージャー）ごとに、持ち主でない・配下でない・公開されていない場合の拒否まで確かめる
- 直す分岐の反対側、つまり今まで動いていた経路も、応答の値まで確かめる
- 境界の値（受講期限の当日と翌日など）を入れる
- 具体例に加えて、どんな入力でも成り立つ性質も検討する。同じ操作を2回行っても結果が変わらないこと（冪等性）などである

## 漏れやすい場面

このリポジトリのレビューで漏れが多かった場面である。変更に関係するものは、確かめるかを検討する。プランを作るときと、テストカバレッジを評価するときもこの一覧を使う。

- 日時や外部キーが空のとき（一度もログインしていない受講生、期限なしの受講など）
- 子が1件もないとき、公開されている子が1件もないとき
- 結合で行が重複するとき（既読の記録が複数あるなど）
- 並び順の値が同じとき。二次の並び順がないと結果が揺れる
- 受講期限の当日と翌日（BR-SHARED-006）

## テストデータ

- 参照データ（マスタなど）はシーダー、それ以外（ユーザーなど）はファクトリで用意する
- 講師のファクトリは、既定で区分がマネージャーの講師を作る。講師としての権限を確かめるテストでは、区分に講師を指定する。指定しないとマネージャーの分岐しか通らず、講師の分岐の誤りを検出できない
- 確かめることに関係しない値を指定しない。同じ形のデータを作るのに関係のない指定が並ぶなら、ファクトリに状態を足す
- 準備も確かめ方も同じテストが複数あるなら、DataProvider でまとめる

## 既存のテストを変えるとき

プランの「変更する振る舞い」に挙げたもの以外のテストが落ちたら、テストを直さずに実装を疑う。期待値を変えたときは、どのテストをなぜ変えたかを PR の説明に書く。
